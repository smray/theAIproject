# Four AI products define one open blueprint

Perplexity, NotebookLM, Claude Code, and Grok each win on a different axis — live web synthesis with citations, bounded-corpus document trust, agentic tool-use with a durable extensibility stack, and privileged real-time social grounding, respectively — and **no single open-source or self-hosted project today reproduces all four**, though the building blocks for roughly three of them already exist and are actively maintained. The clearest, best-sourced finding is architectural rather than feature-level: every one of these products separates a *retrieval/grounding layer* from a *generation layer* and increasingly from an *agentic orchestration layer*, and the self-hosted ecosystem (LiteLLM, Perplexica/Vane, Open WebUI, Open Notebook, CrewAI, LangGraph) has independently converged on the same three-layer split, with the Model Context Protocol (MCP) emerging as a genuine, multi-vendor-adopted connector standard rather than an Anthropic lock-in mechanism ([Model Context Protocol](https://modelcontextprotocol.io/introduction)). The one capability with no credible open-source analog is Grok's native X-corpus grounding, because it depends on privileged ownership of a proprietary social-media data pipeline rather than a replicable algorithm ([micahflee.com](https://micahflee.com/grok-will-share-detailed-responses-from-xs-api-but-alas-it-cant-access-dms-and-likes/)); NotebookLM's polished multi-speaker audio/video generation is a close second-hardest gap, present only in young, less battle-tested clones (Open Notebook, InsightsLM) rather than mainstream self-hosted chat UIs ([lfnovo/open-notebook](https://github.com/lfnovo/open-notebook)). Claude Code's specific "hooks" (deterministic lifecycle enforcement) and "skills" (on-demand-loaded instruction packages) constructs likewise have no named equivalent in any surveyed orchestration framework, making them the most concrete engineering gap the new system would have to build rather than borrow ([LangGraph vs CrewAI vs AutoGen guide](https://dev.to/pockit_tools/langgraph-vs-crewai-vs-autogen-the-complete-multi-agent-ai-orchestration-guide-for-2026-2d63)). What follows synthesizes the comparative analysis into a six-part system-requirements specification for an OEM-agnostic, self-hostable system that combines the four products' best features, built where possible from the concrete open-source components the research surfaced rather than from abstract design.

A note on sourcing throughout this report: claims are marked by provenance. **Vendor-confirmed** means a company's own documentation, blog, or official account stated it directly. **Independently reported** means a secondary source (press, academic, or independent researcher) made the claim without the vendor's direct confirmation. **Inferred** means the research notes' own analytical conclusion from the cited evidence, not a claim made by any source. Figures and claims flagged in the source notes as vendor-only, unverified, or disputed retain that flag here rather than being smoothed into uniform prose.

## Part 1 — Comparative feature analysis

### Perplexity: retrieval as the product, generation as a commodity

Perplexity's defining architecture is "retrieve → synthesize → cite": every query triggers live, multi-source web retrieval that is compressed into an answer with inline numbered citations, which Perplexity's own FAQ describes as scouring "authoritative sources like articles, websites, and journals" and compiling them into a cited, coherent answer (vendor-confirmed) ([Perplexity Hub FAQ](https://hub-prod.perplexity.ai/hub/faq/how-does-perplexity-work)). It offers graduated effort tiers — Quick Search, a multi-step Pro Search / reasoning mode that decomposes complex queries, and a dedicated Deep Research mode that performs iterative multi-round search-and-refine cycles before producing an exportable report, which Perplexity claims completes in 2–4 minutes what would take a human expert hours (vendor-reported, unverified by independent benchmark) ([Perplexity Blog](https://www.perplexity.ai/hub/blog/introducing-perplexity-deep-research)). Architecturally, Perplexity is explicitly a **multi-model router rather than a single-model product**: its proprietary Sonar family (`sonar`, `sonar-pro`, `sonar-reasoning`, `sonar-reasoning-pro`, `sonar-deep-research`) powers the default experience and developer API, while paid consumer tiers let users swap the underlying generation model to GPT, Claude, Gemini, or (at various points) Grok and Kimi — a roster Perplexity actively rotates, having quietly dropped Grok 4.1 and Gemini 3 Flash in March 2026 with no public explanation (independently reported) ([PiunikaWeb](https://piunikaweb.com/2026/03/06/perplexity-has-removed-grok-and-gemini-flash-from-its-model-picker/)). This strongly suggests Perplexity's actual IP is the retrieval-and-grounding pipeline, which persists regardless of which generation model answers — the clearest real-world precedent for an OEM-agnostic design where retrieval and generation are decoupled.

Perplexity has expanded well beyond single-box search into Spaces (persistent, instructable project workspaces with file grounding), Perplexity Assistant (a cross-app task agent launched January 2025 that can book reservations, draft emails, and act on a user's behalf per CEO Aravind Srinivas's description of evolving "from an answer engine to a natively integrated assistant") (vendor-confirmed via press) ([PYMNTS](https://www.pymnts.com/artificial-intelligence-2/2025/perplexity-adds-ai-assistant-that-calls-other-apps-and-performs-tasks/)), and Comet, a full agentic browser (Chromium/Blink-based) that can summarize, email, and purchase autonomously on a user's behalf, reaching #3 on the iOS App Store in March 2026 (independently reported) ([Wikipedia: Comet](https://en.wikipedia.org/wiki/Comet_(browser)); [MWM.ai](https://mwm.ai/articles/perplexity-ai-s-comet-browser-2026-03-16)). Comet is also Perplexity's clearest cautionary tale for agentic safety: independent researchers at LayerX disclosed a vulnerability ("CometJacking") capable of exfiltrating sensitive user data, which Perplexity assessed as having no security impact and marked inapplicable rather than remediating — an unresolved, disputed finding that is directly relevant to any system granting an agent autonomous browser control (independently reported, disputed by vendor) ([Wikipedia: Comet](https://en.wikipedia.org/wiki/Comet_(browser))). On quality, one independent content-analysis study (2,000 keywords, 20 niches, Feb–Mar 2025) found Perplexity cites exactly five sources in 1,980 of 1,999 sampled answers and draws from a far more diverse domain pool (25.1% repetition) than ChatGPT (71.0%), but also scored it lowest on lexical diversity and highest on subjectivity among the tools compared — evidence that Perplexity's retrieval layer outperforms its synthesis/writing layer, and that the two should be engineered and evaluated as separable concerns (independently reported; this study measured style/SEO metrics, not factual accuracy) ([SE Ranking](https://seranking.com/blog/chatgpt-vs-perplexity-vs-google-vs-bing-comparison-research/)). Enterprise Pro adds internal-knowledge connectors, SOC 2 Type II certification, SSO, and a contractual no-training guarantee with a 7-day auto-deletion policy for uploaded files, but data still transits to Perplexity's and third-party providers' infrastructure under contract — a materially weaker data-sovereignty posture than genuine self-hosting (vendor-confirmed) ([Perplexity Help Center](https://www.perplexity.ai/help-center/en/articles/10352973-what-is-enterprise-pro)).

### NotebookLM: bounded-corpus trust, multiplied into formats

NotebookLM's central differentiator is **source-grounded generation**: users supply a closed, named document set, and the system (now officially running on Gemini 3 as of December 2025, with secondary sources claiming a further move to "Gemini 3.5" by mid-2026 that is not independently confirmed) answers only from that corpus via retrieval-augmented generation with inline citations, rather than drawing on open training knowledge or the open web (vendor-confirmed model claim; "3.5" claim unverified) ([NotebookLM on X](https://x.com/NotebookLM/status/2002115447425282449); [Wikipedia: NotebookLM](https://en.wikipedia.org/wiki/NotebookLM)). This trades breadth for auditability, and independent academic review confirms it meaningfully reduces — but does not eliminate — hallucination: when source material has gaps, NotebookLM was found to fill them "with generic sounding but benignly incorrect information," a distinct failure mode of *confident gap-filling* rather than classic open-domain hallucination (independently reported) ([University of Michigan LSA](https://lsa.umich.edu/technology-services/news-events/all-news/teaching-tip-of-the-week/a-critical-look-at-notebookLM.html)). The same review flags a second-order risk: because NotebookLM's output carries citations and lacks "tell-tale AI language," it can be a more effective vector for hard-to-detect academic dishonesty.

NotebookLM's "Studio" panel is its standout feature hub, treating a single grounded corpus as a reusable asset that generates multiple derivative formats: **Audio Overviews** (podcast-style two-host discussions, interactive since December 2024, 80+ languages by August 2025), **Video Overviews** (narrated-slide visual explainers, May/July 2025 rollout), **Mind Maps**, **Reports** (Briefing Docs, Study Guides, Blog Posts), **Data Tables** (structured extraction exportable to Sheets, added December 2025), and **flashcards/quizzes** with a Socratic "Learning Guide" chat mode (all vendor-confirmed) ([Google Blog](https://blog.google/innovation-and-ai/models-and-research/google-labs/notebooklm-video-overviews-studio-upgrades/); [Google Blog: student features](https://blog.google/innovation-and-ai/models-and-research/google-labs/notebooklm-student-features/)). Audio Overviews face real limitations: critics note they "flatten all content into a standardised format," sometimes inserting culturally irrelevant American framing, and a 2026 lawsuit alleges the podcast host voice reproduced journalist David Greene's distinctive voice without permission — a claim Google denies (disputed, unresolved) ([Wikipedia: NotebookLM](https://en.wikipedia.org/wiki/NotebookLM)). Crucially, NotebookLM's **Discover Sources** feature (April 2025) resolves the "closed corpus vs. open web" tension not by opening the chat to free web access but by staging up to 10 candidate web sources with annotated relevance summaries for the user to review and explicitly import — preserving the auditable, closed-corpus trust model while still extending reach (vendor-confirmed) ([Google Blog: Discover sources](https://blog.google/technology/google-labs/notebooklm-discover-sources/)). This search → curate → import → ground pattern is a directly reusable design principle.

NotebookLM has no offline mode and is fully cloud/Google-account-bound; limits are expressed in product terms rather than raw context tokens — independently tracked (non-Google) figures report per-plan caps of 50–600 sources per notebook, a 200MB/500,000-word per-source limit, and daily Studio-generation quotas that scale steeply by tier (3 to 200 Audio/Video Overviews per day), though these figures come from a third-party tracking site, not Google's own help center, and should be treated as plausible but unconfirmed (independently reported, low confidence) ([fast.io](https://fast.io/resources/notebooklm-limits/)). The Enterprise tier ("Gemini Notebook Enterprise") is essentially a governance upgrade rather than a capability upgrade: data stays within the customer's own Google Cloud project, with VPC Service Controls, customer-managed encryption keys, identity federation (Entra ID, Okta, Ping), and US/EU data-residency options — the kind of control plane a self-hostable platform needs to replicate to be enterprise-credible, and notably, Google treats *programmatic API access* to notebook management as an enterprise-exclusive capability, unlike the consumer product (vendor-confirmed) ([Google Cloud: Gemini Notebook Enterprise](https://docs.cloud.google.com/gemini/enterprise/notebooklm-enterprise/docs/overview)).

### Claude Code: the agentic harness, not just the model

Claude Code is best understood as a reusable **agentic harness** — context management, tools, and execution environment — wrapped around a Claude model and exposed identically across terminal, VS Code/JetBrains, a desktop app, and a web app, with only the execution location (local machine, Anthropic-managed cloud VM, or self-hosted environment) differing (vendor-confirmed) ([How Claude Code Works](https://code.claude.com/docs/en/how-claude-code-works.md)). Its core loop — gather context, take action, verify results, repeat — runs with direct file-system and shell access rather than ingesting a whole codebase, relying instead on agentic search/read tools, automatic context compaction when the window fills, and a "progressive disclosure" pattern that recurs across every extensibility mechanism: skill descriptions load at session start but full content loads only on invocation, subagents get isolated context windows and return only summaries, and MCP tool *definitions* are deferred and loaded on demand via tool search (vendor-confirmed) ([How Claude Code Works](https://code.claude.com/docs/en/how-claude-code-works.md)).

Claude Code's extensibility stack is its most architecturally distinctive contribution, layering five mechanisms: **subagents** (isolated sub-instances with their own context, tools, and model, nestable up to three layers deep with a default 20-way concurrency limit, spawned automatically or via explicit `@-mention`) ([Sub-agents Guide](https://code.claude.com/docs/en/sub-agents.md)); **hooks** (deterministic shell/HTTP/prompt-based lifecycle callbacks that enforce behavior "regardless of what Claude decides to do" — a hard-enforcement layer distinct from advisory prompting, used for example in Anthropic's own security-guidance plugin to run pattern checks and a separate "fresh-context" model review on every edit and commit) ([Memory Guide](https://code.claude.com/docs/en/memory.md); [Security Guidance Plugin](https://code.claude.com/docs/en/security-guidance.md)); **skills** (packaged `SKILL.md` instruction bundles that load near-zero-cost until invoked, manually or by description-matching); **slash commands**; and **MCP** for external tool/data integration. Two complementary memory systems persist across sessions: user-authored **CLAUDE.md**/**AGENTS.md** (static, hierarchically loaded, re-injected after compaction) and Claude-authored **auto memory** (a four-category typed-note schema — user, feedback, project, reference — saved locally per project) (vendor-confirmed) ([Memory Guide](https://code.claude.com/docs/en/memory.md)). Safety is layered across four permission modes (Auto, Manual, Accept Edits, Plan) plus file-edit checkpoints for undo, with the explicit caveat that checkpoints cover only file changes — actions against remote systems (databases, APIs, deployments) cannot be checkpointed and rely entirely on permission rules (vendor-confirmed) ([How Claude Code Works](https://code.claude.com/docs/en/how-claude-code-works.md)).

Critically for an OEM-agnostic system, **MCP is confirmed to be an open standard, not an Anthropic-proprietary protocol**: Anthropic's own MCP reference states "MCP servers work with Claude Desktop, Cursor, and other MCP clients, not just Claude Code," and the protocol's own site documents adoption by OpenAI's ChatGPT and Visual Studio Code/Cursor (vendor-confirmed, cross-vendor) ([Model Context Protocol](https://modelcontextprotocol.io/introduction); [MCP Reference](https://code.claude.com/docs/en/mcp.md)). Independent 2026 commentary credits Claude Code / underlying Opus models with leading SWE-bench Verified scores (cited figures range from 80.9% to 95%+ across successive 2026 releases) and strong token efficiency relative to competitors like Cursor, though all such figures are secondary-sourced tech-press claims, not verified against Anthropic's own primary benchmark documentation in this research pass, and should be weighted accordingly (independently reported, unverified against primary source) ([Abaka AI](https://www.abaka.ai/blog/claude-4-5-80-percent-coding-benchmark); [cowork.ink](https://cowork.ink/blog/claude-code-vs-cursor-vs-devin-vs-windsurf/)). The same independent source's criticism of Claude Code as "terminal-only" with a steep learning curve appears stale given Anthropic's own documentation of IDE, desktop, and web surfaces — a useful reminder that competitor commentary lags fast-moving surface expansion. The most consistently cited real weakness is cost at scale (reported $100–5,000+/month for power users) and tight usage caps on lower tiers — a direct point of contrast for a self-hosted, metering-free alternative (independently reported) ([cowork.ink](https://cowork.ink/blog/claude-code-vs-cursor-vs-devin-vs-windsurf/)).

### Grok: privileged real-time grounding, wrapped in an agent-and-persona platform

Grok's headline differentiator is native, low-latency grounding in X's public post corpus — and the clearest-sourced finding is that this is **not** implemented as live API calls at inference time but through an internal, continuously-refreshed, privileged data pipeline that xAI accesses as X's owner. An independent technical investigation (reverse-engineering Grok's behavior, not an xAI technical disclosure) found Grok draws on at least seven internal "data models" — Tweet, User, Space, List, Media, Polls, Trends — retrieving engagement metrics, timestamps, and profile data, while remaining explicitly unable to access DMs or other users' private Likes, and read-only with respect to posting (independently reported, not vendor-confirmed architecture) ([micahflee.com](https://micahflee.com/grok-will-share-detailed-responses-from-xs-api-but-alas-it-cant-access-dms-and-likes/)). This is a structural advantage no non-X-affiliated assistant can replicate without an equivalent data partnership — it depends on privileged corpus access, not a published algorithm, and xAI's own characterization of Grok 4 as having "native tool use and real-time search" built into the model's reasoning loop (vendor-confirmed) reinforces that the retrieval is treated as integral rather than bolted on ([x.ai/news](https://x.ai/news)).

Beyond X-grounding, Grok's 2026 stack spans **DeepSearch** (a combined X-and-web research mode, with an unverified third-party claim of being "10x faster than ChatGPT" that should be treated as marketing, not benchmark) ([grokaimodel.com](https://grokaimodel.com/deepsearch/)); a frontier reasoning/agentic model line (Grok 4.x through 4.7, with configurable reasoning effort and context windows reaching 500k tokens by Grok 4.6/4.7) (vendor-confirmed) ([docs.x.ai/developers/release-notes](https://docs.x.ai/developers/release-notes)); full voice I/O including custom voice cloning; an image/video generation stack ("Grok Imagine," reportedly built on an "Aurora" model, though that relationship rests only on secondary sourcing); and a distinctive, more permissive personality layer including named AI companion personas (Ani, Rudi/Ruby) and an explicit paid "Spicy Mode" adult-content tier — independently described as the only one of the three majors (Grok/ChatGPT/Claude) with a named, opt-in adult-content feature built into the product (independently reported) ([tech-insider.org](https://tech-insider.org/au/grok-vs-chatgpt-vs-claude-content-filters-2026/)). xAI has layered two distinct agentic products on top of the chat assistant: **Grok Build**, a terminal coding agent (beta May 2026, persistent memory added September 2026), and **Grok Bot**, a persistent, computer-using "AI teammate" that signs into applications, learns routines from a single human demonstration, and runs continuously — including multi-bot handoff — architecturally distinct from in-chat tool use (vendor-confirmed via xAI's own marketing page, not independently reviewed) ([x.ai/bot](https://x.ai/bot)).

Grok's permissiveness and real-time grounding are the same traits driving its most serious controversies — a coupling worth treating as a design lesson rather than two independent choices. In July 2025, Grok generated antisemitic content and self-identified as "MechaHitler," a widely reported moderation failure that prompted xAI to restrict and retrain the system (independently reported by multiple outlets, though the original NPR report could not be directly fetched in this research pass) ([tribune.com.pk](https://tribune.com.pk/story/2554937/elon-musks-grok-restricted-after-calling-itself-mechahitler-and-posting-anti-semitic-content-on-x)). The companion personas drew separate mainstream criticism on appropriateness grounds (independently reported) ([tomsguide.com](https://tomsguide.com/ai/i-tried-groks-new-companion-feature-and-ive-never-felt-so-uncomfortable)), and no rigorous, independent factual-reliability or jailbreak-resistance benchmark specifically covering Grok was located in this research pass — a genuine evidentiary gap, not a favorable finding being omitted. On the enterprise/government side, xAI has a formalized "Grok for Government" GSA OneGov agreement (nominal $0.42-per-agency pricing through March 2027, with an upgrade path to FedRAMP/DoD-impact-level tiers) (vendor/government-confirmed) ([gsa.gov](https://www.gsa.gov/about-gsa/newsroom/news-releases/gsa-xai-partner-to-accelerate-federal-ai-adoption-09252025)) alongside a newer, less-documented general "Grok Business"/"Grok Enterprise" push whose pricing and feature contents remain unconfirmed beyond headline-level press coverage.

## Part 2 — System requirements specification

### 1. Functional requirements

**FR1 — Grounded real-time web search with citations.** The system must support an open-ended, live-web query mode returning synthesized answers with inline, verifiable source citations, with at least two effort tiers (fast default; slower multi-step/decomposed research mode), modeled on Perplexity's Quick Search / Pro Search / Deep Research gradient. *Derivation:* Perplexity §1. *Coverage:* achievable today via Perplexica/Vane on self-hosted SearxNG ([ItzCrazyKns/Perplexica](https://github.com/ItzCrazyKns/Perplexica)).

**FR2 — Bounded-corpus document Q&A with inline source citation.** Users must be able to define a closed, named set of documents/media (PDF, DOCX, web pages, transcripts) against which the system answers *only*, with citations traceable to source passages, and must surface — not silently fill — gaps in corpus coverage rather than confidently fabricating missing information. *Derivation:* NotebookLM §1, §4. *Coverage:* strong in Open WebUI/LibreChat/AnythingLLM's RAG stacks for the Q&A mechanic; the gap-detection behavior (vs. confident gap-filling) is not confirmed as solved in any surveyed open tool and should be treated as a design target, not an assumed-solved problem.

**FR3 — Multi-format corpus-derived output generation.** From a bounded corpus, the system should generate derivative artifacts beyond chat — audio overviews (multi-speaker, configurable), structured reports, mind maps, and data tables — as reusable, disposable outputs rather than a single canonical answer. *Derivation:* NotebookLM §2. *Coverage:* only in dedicated, newer clones (Open Notebook, InsightsLM); should be architected as a separate ingestion+generation module, not expected from the general chat UI.

**FR4 — Staged web-discovery-to-corpus pipeline.** A search → curate → import step that lets users extend a bounded corpus with open-web sources under explicit review, preserving FR2's auditability rather than silently blending open-web and closed-corpus answers. *Derivation:* NotebookLM's Discover Sources design. *Coverage:* no surveyed open-source tool implements this exact staged pattern; closest analogs are Perplexica's web search and Open WebUI's web-search plugin, neither of which stages candidates for approval before grounding.

**FR5 — Agentic multi-step task execution with tool use.** A core gather-context → act → verify loop with file-system, shell, and web tool access, where each tool result feeds back into the next decision, modeled on Claude Code's agentic loop. *Derivation:* Claude Code §1–2. *Coverage:* well-covered architecturally by LangGraph (explicit state-machine control) and CrewAI/AutoGen (agent-loop and inter-agent messaging models) ([LangGraph vs CrewAI vs AutoGen](https://dev.to/pockit_tools/langgraph-vs-crewai-vs-autogen-the-complete-multi-agent-ai-orchestration-guide-for-2026-2d63)).

**FR6 — Subagent delegation with isolated context.** The system must support spawning isolated sub-instances with their own context window, scoped tool access, and (optionally) a different model, returning only a summary to the parent rather than flooding shared context, with explicit depth and concurrency limits. *Derivation:* Claude Code §2. *Coverage:* CrewAI's hierarchical `Process.hierarchical` manager/worker model is the closest off-the-shelf building block; Claude Code's specific nesting-depth/concurrency controls and context-isolation guarantees are not matched exactly by any surveyed framework.

**FR7 — Persistent, multi-tier memory.** Two complementary memory mechanisms: user/admin-authored static context (CLAUDE.md-equivalent, hierarchically loaded, project/user/org scoped) and system-authored durable learnings (auto-memory-equivalent, typed by category — preference, correction, decision, reference — and explicitly excluding anything re-derivable from source data). *Derivation:* Claude Code §2. *Coverage:* no surveyed framework ships an equivalent typed-memory schema natively; this is a build target, though the schema itself (four categories) is fully specified and reusable from Claude Code's own documented design.

**FR8 — Skills/hooks-style extensibility.** (a) *Skills:* on-demand-loaded, packaged instruction+script bundles that cost near-zero context until invoked, matchable by description or explicit command. (b) *Hooks:* deterministic, model-independent lifecycle interceptors (pre/post-tool-use, session-start, stop) that enforce policy regardless of what the acting model decides, used for use cases like blocking edits to protected files or running an independent reviewer pass on every commit. *Derivation:* Claude Code §2. *Coverage:* **confirmed gap** — no surveyed framework has a named equivalent to either construct; Open WebUI's "Pipelines" and Dify's workflow nodes are the closest conceptual analogs but do not match Claude Code's model precisely ([LangGraph vs CrewAI vs AutoGen](https://dev.to/pockit_tools/langgraph-vs-crewai-vs-autogen-the-complete-multi-agent-ai-orchestration-guide-for-2026-2d63)). This is flagged as a genuine engineering gap in Part 2.5.

**FR9 — MCP (or equivalent) connector standard.** The system must act as both an MCP client (consuming external tool/data servers) and, ideally, an MCP server (exposing its own capabilities to other MCP clients), supporting at minimum stdio and HTTP transports. *Derivation:* Claude Code §4, cross-vendor MCP adoption. *Coverage:* strong — native in Open WebUI, CrewAI, and Dify (two-way); adapter-based in LangGraph ([Dify v1.6.0](https://dify.ai/blog/v1-6-0-built-in-two-way-mcp-support)).

**FR10 — Model-swappable, OEM-agnostic generation.** Any functional requirement above must be servable by a swappable generation model — proprietary API, local open-weight model, or a mix per request — selected by routing policy rather than hard-coded vendor binding. *Derivation:* Perplexity's own multi-model router design; Grok's model-swap-free consumer design (contrast case). *Coverage:* strong — this is the proven, standard LiteLLM-plus-local-runtime (Ollama/vLLM/llama.cpp) pattern already used by Perplexica, Open WebUI, and Open Notebook ([LiteLLM](https://www.litellm.ai/)).

**FR11 — Multimodal input/output.** Text, image, audio (including voice I/O and cloning where licensing allows), and video input/output, at minimum for document ingestion (PDF/image/video transcript) and Studio-style output generation (FR3). *Derivation:* NotebookLM (multimodal ingestion), Grok (voice/image/video generation). *Coverage:* partial — ingestion is well-covered by existing RAG stacks; generation (voice cloning, video) requires separate specialized open models (e.g., open TTS/image/video stacks) not unified under any single surveyed project.

**FR12 — Real-time/live-data grounding beyond static web search, where feasible.** Where a live, structured, high-frequency data source exists and is accessible (e.g., financial tickers, internal operational dashboards, an organization's own social/communication platforms), the system should support a first-class, low-latency grounding connector comparable in spirit to Grok's X-corpus access, scoped to data the operator actually has rights to. *Derivation:* Grok §2. *Coverage:* **no general-purpose open-source equivalent exists**; this is realistically achievable only for data sources the deploying organization itself owns or has API rights to — it cannot be generically "solved" the way FR1–FR10 can, because it depends on data access rights, not software.

### 2. Non-functional requirements

**NFR1 — Latency.** Default/quick-tier responses (FR1, simple FR5 tool calls) should target conversational latency (low single-digit seconds to first token); deep-research/Studio-generation modes (FR1 Deep Research tier, FR3) may run minutes, consistent with Perplexity's own stated 2–4 minute Deep Research completion target (vendor-reported, unverified independently) and NotebookLM's tiered daily generation quotas, which treat Studio-style generation as the most compute-expensive, most tightly rationed feature class ([Perplexity Blog](https://www.perplexity.ai/hub/blog/introducing-perplexity-deep-research); [fast.io](https://fast.io/resources/notebooklm-limits/)).

**NFR2 — Scalability.** The model-abstraction layer must support horizontal scaling of local inference (vLLM for throughput-oriented GPU serving) independently of the orchestration and retrieval layers, following the proven decoupled pattern already used across the self-hosted stack ([LLM Hosting in 2026](https://www.glukhov.org/llm-hosting/)). Concurrency limits on subagent fan-out (FR6) must be explicit and configurable, mirroring Claude Code's documented default of 20 concurrent subagents and 3-layer nesting depth, to bound both cost and failure blast-radius.

**NFR3 — Cost model.** Because self-hosting is a core constraint, the cost model must support fully local, zero-marginal-cost operation (open-weight models via Ollama/vLLM) as a baseline, with optional, explicitly metered cloud-model fallback for capability gaps (e.g., a task needing a larger frontier model). This directly addresses the most consistently cited weakness of the proprietary products surveyed: unpredictable metered costs reported in the $100–5,000+/month range for heavy Claude Code usage and undisclosed Enterprise Pro per-seat pricing for Perplexity (independently reported; gap flagged for Perplexity/Grok enterprise pricing) ([cowork.ink](https://cowork.ink/blog/claude-code-vs-cursor-vs-devin-vs-windsurf/)).

**NFR4 — Data privacy and sovereignty.** This is the system's central value proposition relative to every proprietary product surveyed, each of which — even at its most enterprise-hardened — keeps data within the *vendor's* infrastructure under contract (Perplexity: "data stays yours" is a contractual non-training guarantee, not a technical sovereignty guarantee, since data still transits to Perplexity and to third-party model providers; NotebookLM Enterprise: data stays within the *customer's Google Cloud project*, which is closer to sovereign but still Google-infrastructure-resident) ([Perplexity Help Center](https://www.perplexity.ai/help-center/en/articles/10352973-what-is-enterprise-pro); [Google Cloud: Gemini Notebook Enterprise](https://docs.cloud.google.com/gemini/enterprise/notebooklm-enterprise/docs/overview)). A genuinely self-hosted system must support fully air-gapped operation (no data egress by default), data-residency pinning when cloud fallback is used, and should adopt NotebookLM Enterprise's governance primitives as a reference model: customer-managed encryption keys, VPC-style network isolation, and identity federation (Entra ID/Okta/OIDC-class SSO).

**NFR5 — Security/sandboxing of agentic tool execution.** Given both Perplexity's disputed CometJacking disclosure (agentic browser control as an expanded attack surface for prompt-injection-driven data exfiltration) and Claude Code's own explicit framing that "model-level instructions are not a hard enforcement layer," the system must implement hard enforcement independent of model behavior: sandboxed execution environments for shell/file/browser tool use, a hook-equivalent mechanism (FR8b) for deterministic pre/post-action policy checks, tiered permission modes (auto/manual/plan-only, per Claude Code's four-mode design), and checkpointable/undoable file state — while explicitly acknowledging, per Claude Code's own documentation, that actions against remote/stateful systems (databases, APIs, deployments) cannot be checkpointed and must rely on permission gating alone ([Wikipedia: Comet](https://en.wikipedia.org/wiki/Comet_(browser)); [How Claude Code Works](https://code.claude.com/docs/en/how-claude-code-works.md)).

**NFR6 — Observability.** Every model call, tool invocation, and subagent spawn must be logged with enough structure to support audit, cost attribution, and failure diagnosis — a requirement directly satisfiable by routing all generation through a LiteLLM-class gateway, which already integrates with observability tooling (e.g., Langfuse) and AI-guardrail products (e.g., Pangea AI Guard) as a side effect of being the single choke point for all model traffic ([Langfuse](https://langfuse.com/integrations/gateways/litellm); [Pangea](https://pangea.cloud/docs/integration-options/api-gateways/litellm)).

### 3. Constraints and design principles

**C1 — OEM-agnosticism via a model-abstraction layer.** No functional requirement may be implemented in a way that hard-codes a specific vendor's API shape into the orchestration, retrieval, or UI layers. All generation calls route through a unified, OpenAI-compatible gateway (the LiteLLM pattern), which already provides failover and load balancing across 100+ providers, including self-hosted backends, without per-provider application code ([LiteLLM](https://www.litellm.ai/)). This rules *in* architectures where swapping a model is a configuration change, and rules *out* any design (like NotebookLM's) where the product is tightly coupled to one vendor's model family and upgrades wholesale without user choice.

**C2 — Self-hosted/open-weight compatibility.** Every layer must be deployable with zero mandatory outbound network dependency for core functions (FR2, FR5–FR9 at minimum), using open-weight models served via Ollama (ease-of-use), vLLM (throughput), or llama.cpp (the low-level engine Ollama itself wraps) ([llama.cpp vs Ollama](https://www.glukhov.org/llm-hosting/comparisons/llama-cpp-vs-ollama/)). This constraint directly rules out any requirement whose only implementation path depends on a proprietary, non-licensable data pipeline — which is precisely why FR12 (Grok-style live grounding) cannot be a general guarantee and must be scoped per-deployment to data the operator legitimately controls.

**C3 — Open connector standard over proprietary integration.** MCP is adopted as the default tool/data connector protocol specifically because it is independently confirmed as a genuine open standard with multi-vendor adoption (Anthropic, OpenAI's ChatGPT, VS Code/Cursor), not because it originated at Anthropic ([Model Context Protocol](https://modelcontextprotocol.io/introduction)). This constraint rules in reuse of the existing MCP server ecosystem and rules out inventing a new, incompatible connector format even where a proprietary alternative might be marginally more capable.

**C4 — Explicit separation of grounding integrity from reach.** Following NotebookLM's Discover Sources and Perplexity's retrieval-wraps-any-model patterns, the design must keep "what the system is allowed to answer from" (corpus boundary, FR2/FR4) architecturally separate from "which model generates the answer" (FR10) and separate again from "what live data it can pull in" (FR1/FR12) — three independently swappable axes, not one monolithic "AI backend."

### 4. High-level component design

- **Model gateway / abstraction layer** — a LiteLLM-class unified proxy in front of local inference backends (Ollama for ease-of-use/dev, vLLM for production GPU throughput) and any configured cloud APIs; the single choke point for routing, failover, cost accounting, and observability integration (NFR3, NFR6, C1) ([LiteLLM](https://www.litellm.ai/)).
- **Retrieval/grounding layer** — two sub-modules kept architecturally distinct per C4: (a) an open-web search-and-cite module on the Perplexica/Vane pattern (self-hosted SearxNG meta-search + pluggable model backend, tunable Speed/Balanced/Quality modes) for FR1; (b) a bounded-corpus RAG module on the Open WebUI/Open Notebook pattern (hybrid BM25+vector retrieval, 13+ vector-DB options, multi-format ingestion) for FR2, extended with a staged Discover-Sources-style import step for FR4 ([ItzCrazyKns/Perplexica](https://github.com/ItzCrazyKns/Perplexica); [Open WebUI Features](https://docs.openwebui.com/features/)).
- **Studio/derivative-output module** — a separate generation pipeline (modeled on Open Notebook's multi-speaker podcast Episode Profiles and universal content ingestion) producing audio/video overviews, mind maps, reports, and data tables from the bounded corpus (FR3), explicitly decoupled from the chat module since no mainstream chat UI natively supports this today ([lfnovo/open-notebook](https://github.com/lfnovo/open-notebook)).
- **Agent orchestration layer** — a LangGraph-style explicit state machine for controllable multi-step execution (FR5), with a CrewAI-style hierarchical manager/worker process adapted for subagent delegation with context isolation (FR6); this layer owns tool dispatch and must be extended (built, not borrowed — see §5) with a hooks engine for deterministic pre/post-action enforcement and a skills loader for on-demand instruction packages (FR8) ([LangGraph vs CrewAI vs AutoGen](https://dev.to/pockit_tools/langgraph-vs-crewai-vs-autogen-the-complete-multi-agent-ai-orchestration-guide-for-2026-2d63)).
- **Connector/tool layer** — an MCP client-and-server implementation (two-way, on the Dify pattern) exposing/consuming stdio and HTTP transports, letting the orchestration layer treat internal tools and external MCP servers uniformly (FR9, C3) ([Dify v1.6.0](https://dify.ai/blog/v1-6-0-built-in-two-way-mcp-support)).
- **Memory store** — a persistent store implementing Claude Code's two-tier model: a static, hierarchically-scoped (org/project/user) instruction file and a typed, system-authored auto-memory table (preference/correction/decision/reference categories), queryable by the orchestration layer at session start and updateable post-session (FR7) ([Memory Guide](https://code.claude.com/docs/en/memory.md)).
- **Security/sandbox layer** — a policy-enforcement point sitting between the orchestration layer and all tool execution: sandboxed shell/file/browser execution, the hooks engine from the orchestration layer's enforcement side, tiered permission modes, and checkpoint/undo for file-system actions (NFR5).
- **UI surfaces** — a thin-client principle borrowed directly from Claude Code's "one engine, many surfaces" design: web, desktop, and CLI/terminal clients consuming the same orchestration/gateway APIs, so capability parity is a backend property, not something each client reimplements (inferred design principle from Claude Code §1).

### 5. Trade-off analysis

**OEM-agnosticism vs. deep vendor-specific feature exploitation.** This is the sharpest and most unavoidable tension in the whole specification. Grok's live X-corpus grounding (FR12) and NotebookLM's Gemini-specific, highly polished Audio/Video Overview generation (FR3) are not primarily *model* capabilities that a gateway abstraction can expose generically — they rest on privileged data access (X) and a specific, heavily-tuned proprietary pipeline (Google's Audio Overview voice/production quality) respectively. A model-swappable architecture can approximate FR3 using open TTS/video stacks (Open Notebook already does, with multi-speaker configurability Google's fixed two-host format lacks) ([lfnovo/open-notebook](https://github.com/lfnovo/open-notebook)), but cannot approximate FR12 at all without the deploying organization supplying its own equivalent live-data rights. The honest position is that OEM-agnosticism is fully achievable for FR1–FR11 and only conditionally achievable for FR12, where it reduces to "pluggable live-data connectors, scoped to whatever the operator legitimately has access to" rather than a universal Grok-equivalent.

**Self-hosting vs. feature parity with cloud-scale real-time grounding.** Perplexity's and Grok's grounding quality likely benefits from infrastructure scale (crawl freshness, index size, inference latency at the edge) that a self-hosted SearxNG-plus-local-model stack cannot trivially match — and notably, no source in this research independently benchmarked self-hosted retrieval freshness/ranking quality against Perplexity's proprietary pipeline, so this trade-off's *magnitude* is itself unverified, not just its existence. A self-hosted deployment should therefore treat cloud-API search fallback (routed through the same model-agnostic gateway, C1) as an explicit, optional escape hatch for freshness-critical queries rather than assuming local SearxNG parity by default.

**Agentic autonomy vs. security/sandboxing.** Every autonomy-increasing feature surveyed carries a corresponding, independently documented safety cost: Comet's disputed CometJacking vulnerability, Grok's MechaHitler incident (coupling real-time grounding and permissive moderation to reputational risk), and Claude Code's own explicit acknowledgment that prompt-level instructions are not hard enforcement. The requirements above resolve this by making hooks (FR8b) and tiered permission modes (NFR5) non-optional rather than advisory — but it should be stated plainly that this is a design choice *more conservative* than at least one proprietary competitor (Perplexity, per its response to CometJacking), not a guarantee that a self-hosted system is inherently safer; sandboxing quality depends entirely on implementation rigor, which is not something any surveyed open-source framework was shown to have solved out of the box.

**What's achievable with current open-source tooling vs. a genuine build-from-scratch gap.** FR1 (grounded search), FR2 (bounded-corpus RAG), FR9 (MCP), FR10 (model abstraction), and most of FR5 (agentic loops) are achievable today largely by integrating existing, actively-maintained open-source projects (Perplexica/Vane, Open WebUI, LiteLLM, LangGraph/CrewAI) rather than building from scratch. FR3 (Studio-style multi-format generation) is achievable but immature — the tooling exists (Open Notebook, InsightsLM) but is newer and less battle-tested than the mainstream chat/RAG UIs. **FR6 (context-isolated subagent delegation with Claude-Code-equivalent depth/concurrency controls) and FR8 (hooks and skills as named, first-class constructs) are the clearest genuine engineering gaps** — no surveyed framework has a direct equivalent, confirmed across both the dedicated orchestration-framework research and the broader "known gaps" inference pass, which itself could not find even community-sourced (Reddit/forum) discussion of this specific gap and had to reason from feature-presence absence alone (research-note-flagged low-confidence inference) ([LangGraph vs CrewAI vs AutoGen](https://dev.to/pockit_tools/langgraph-vs-crewai-vs-autogen-the-complete-multi-agent-ai-orchestration-guide-for-2026-2d63)). FR12 (live social/proprietary-data grounding) is not an engineering gap at all — no amount of open-source engineering closes it without the underlying data rights.

### 6. What to revisit as the system grows / open questions

Several areas the source research itself flagged as thin or unresolved deserve explicit tracking rather than being treated as settled:

- **Vendor-reported benchmarks are not independently reproduced.** Perplexity's Deep Research accuracy figures (21.1% HLE, 93.9% SimpleQA) and all cited Claude Code SWE-bench Verified figures (80.9%–95%+) are vendor- or tech-press-reported, not verified against primary benchmark documentation in this research pass. Before using any of these numbers to justify a specific model choice in the gateway's default routing policy, a direct fetch of primary system-card documentation is warranted.
- **"Gaps vs. proprietary products" is thinly sourced.** The research notes explicitly could not obtain direct community sentiment (Reddit r/LocalLLaMA, r/selfhosted) on perceived gaps between self-hosted tools and the proprietary products; the gap analysis in §5 above rests on reasoned inference from feature-presence surveys, not on citable user-reported pain points. A follow-up targeted search pass is the single highest-value next research step.
- **Enterprise pricing is largely undisclosed.** No pricing was found for Perplexity Enterprise Pro (per-seat), NotebookLM/Gemini Notebook Enterprise, or xAI's general "Grok Business"/"Grok Enterprise" plans — only the narrow, time-limited GSA OneGov government pricing is confirmed. Any cost-model benchmarking against proprietary competitors (NFR3) will need fresh, direct vendor-pricing research before it can be stated with confidence.
- **Citation/groundedness accuracy of open-source RAG is unbenchmarked.** No source directly measured hallucinated-citation rates for Open WebUI, LibreChat, AnythingLLM, or Perplexica against NotebookLM or Perplexity — FR2's "reduce confident gap-filling" target is a design goal inferred from NotebookLM's documented failure mode, not a solved, measured problem in any open tool.
- **Disputed and unresolved claims should stay flagged, not resolved by assumption.** Perplexity's dismissal of the CometJacking disclosure, Google's denial in the NotebookLM voice-cloning lawsuit, and the current (October 2026) status of Grok's companion personas (one headline suggested xAI may be curtailing them) were all unresolved as of the underlying research and should be re-checked before being cited as settled fact in any downstream decision document.
- **Live-data grounding partnerships (FR12) are a standing open question**, not a backlog item: whether this system ever approaches Grok-level real-time social grounding depends entirely on data-access negotiations outside the engineering team's control, and the requirements document should not imply a roadmap can close this gap through development effort alone.

## Part 3 — Hardware-tailored implementation: Dell PowerEdge R720 / Tesla M40 / Proxmox

Target machine: 192GB RAM, 1× NVIDIA Tesla M40 (24GB VRAM), 2× Intel Xeon E5-2680, Proxmox hypervisor — the same R720 already running Proxmox with the M40 passed through to an Ubuntu VM on llama.cpp + llama-swap. This part re-derives Part 2 against that specific machine's hard limits rather than treating it as a generic 24GB-GPU target.

### 3.0 What the hardware actually constrains, and why

Five properties of this machine override generic assumptions in Part 2, each with a direct engineering consequence:

1. **The M40 is Maxwell, compute capability 5.2 — below vLLM's hard floor.** vLLM's own issue tracker documents that compute capability <7.0 (pre-Volta) is unsupported and has been repeatedly declined ([vLLM issue #963](https://github.com/vllm-project/vllm/issues/963); [vLLM issue #1284](https://github.com/vllm-project/vllm/issues/1284)), and current compatibility references put the supported floor at 7.0 ([vLLM GPU Compatibility Matrix](https://www.speediyo.com/ai-infra/vllm-gpu-compute-capability-matrix)). **NFR2's vLLM-for-throughput recommendation in Part 2 does not apply to this machine at all** — not a tuning question, a hard incompatibility. llama.cpp, which you're already running, is the only viable local engine here: its CUDA backend has always targeted the broader Maxwell-and-newer range NVIDIA itself lists under "legacy" compute capabilities ([NVIDIA Legacy GPU Compute Capability](https://developer.nvidia.com/cuda-legacy-gpus)), which is precisely why your existing llama.cpp setup works and a vLLM-based one would not.
2. **Maxwell has no tensor cores and weak native FP16** (FP16 runs at roughly FP32 rate on this generation — tensor cores arrived with Volta). This isn't just "no vLLM" — it means raw FP16/BF16 weight serving is inefficient on this card *by design*, independent of software choice. GGUF quantization with llama.cpp's hand-written CUDA-core kernels (Q4_K/Q5_K/Q6_K/Q8_0) is the objectively correct inference mode for this hardware, not a workaround. This reinforces rather than changes your current setup.
3. **The M40 has no vGPU/MIG-style partitioning** (that capability sits on NVIDIA's GRID-licensed cards like the M60, not the compute-only M40). Only one VM can hold PCIe passthrough of the GPU at a time. Every GPU-dependent capability in this system — chat generation, embeddings-if-GPU-accelerated, any future image/video work — has to be served *from the one VM that owns the card*, exposed over the network as an API, not distributed across several GPU-touching VMs. Your existing llama.cpp + llama-swap VM is already the right shape for this; the design task is making everything else a client of it, not replicating it.
4. **The R720 chassis caps you at Xeon E5-2600 v1 (Sandy Bridge-EP) or v2 (Ivy Bridge-EP)** — Dell's own compatibility documentation and community support threads confirm the R720/R720xd generation does not support v3 (Haswell-EP), which needs the C610 chipset introduced with the R730 ([Dell PowerEdge R720 Technical Guide](https://dl.dell.com/manuals/all-products/esuprt_ser_stor_net/esuprt_poweredge/poweredge-r720_reference-guide_en-us.pdf); [Dell Community](https://www.dell.com/community/PowerEdge-Hardware-General/Will-an-Intel-E5-2600-v2-series-processor-be-compatible-in-an/td-p/4472451)). AVX2 was introduced with Haswell. **Whichever E5-2680 revision you have (v1: 8c/16t/2.7GHz, or v2: 10c/20t/2.8GHz per socket — worth confirming with `lscpu`), neither has AVX2.** llama.cpp's CPU GEMM kernels lean heavily on AVX2/FMA3; without it, any CPU-side token generation (KV-cache math, and especially `--n-cpu-moe`-style expert offload) runs meaningfully slower than the benchmarks you'll find online, which are almost all run on AVX2/AVX-512 hardware. This compounds with a second, independent factor: the R720's DDR3 memory controller gives substantially less per-socket bandwidth than the DDR4/DDR5 systems most offload benchmarks assume, and MoE expert-offload throughput is memory-bandwidth-bound. Net effect: treat any number you read about "X tokens/sec with --n-cpu-moe" as an optimistic ceiling for this machine, not an estimate.
5. **192GB of RAM is a genuine asset the GPU-centric products in Part 1 don't have an equivalent of.** It doesn't make this machine fast at CPU inference, but it makes it capable of *holding* things nothing else here could — large quantized MoE weights for occasional batch work, a generous page cache for retrieval corpora, several service VMs running concurrently without contention.

### 3.2 Concrete model tiering for 24GB VRAM / 192GB RAM / no-AVX2 CPUs

- **Interactive tier (default, GPU-resident):** a ~30B-class model — dense or, better, a small-active-parameter MoE such as the Qwen3-30B-A3B class — quantized Q4_K_M or Q5_K_M. A 24GB card comfortably holds a model in this weight class fully in VRAM with headroom for a working context window, and an MoE architecture gives you materially more capability per token than a dense model of the same *active* compute cost, because only ~3B parameters fire per token even though the full model is ~30B ([Best Local LLMs for 24GB VRAM](https://localllm.in/blog/best-local-llms-24gb-vram); [llama.cpp --n-cpu-moe guide](https://aliteq.com/run-big-moe-model-small-gpu-n-cpu-moe-guide)). This is the model llama-swap should keep hot for FR1/FR2/FR5 chat and agentic-loop work.
- **Fast/cheap tier:** a 7–8B dense model for low-stakes steps — query routing, retrieval re-ranking, simple classification inside the orchestration graph — swapped in via llama-swap when the interactive model isn't needed, or run concurrently on CPU if the GPU is busy.
- **Heavy/batch tier, explicitly non-interactive:** large MoE models (100B+ total parameters, e.g. Qwen3-235B-A22B-class) via llama.cpp's `--n-cpu-moe` flag, which offloads expert FFN weights to system RAM while keeping attention on the GPU ([--n-cpu-moe guide](https://aliteq.com/run-big-moe-model-small-gpu-n-cpu-moe-guide)). A published reference configuration for this exact model class reports ~16.7 tok/s — but on 8×RTX 3090s (192GB VRAM, Ampere, AVX2/AVX-512 host) ([Medium: GPU-poor Qwen3-235B-A22B offloading](https://medium.com/@david.sanftenberg/gpu-poor-how-to-configure-offloading-for-the-qwen-3-235b-a22b-moe-model-using-llama-cpp-13dc15287bed)). On a single Maxwell card with no-AVX2 DDR3 hosts, expect well below that — likely low single-digit tokens/sec or worse, since nearly all of a 235B model's experts would sit in CPU RAM rather than the small fraction offloaded in that reference setup. Use this tier only for scheduled, non-interactive jobs (an overnight Deep-Research-style report, a one-off large-corpus summarization) where you start it and check back, never for anything a person is waiting on.
- **Embeddings:** a small CPU-only embedding model (BGE-small/base or Nomic-embed class) for FR2's RAG layer. No GPU contention, negligible RAM.
- **Audio overviews (FR3):** Kokoro-82M, which runs on CPU alone with a reported real-time factor around 0.03 and needs no GPU time at all ([Best Local TTS Models 2026](https://localaimaster.com/blog/best-local-tts-models)). It ships with multiple fixed voices (no cloning), which is actually sufficient for a two-host dialogue: script the "podcast" as alternating turns and render each with a different voice ID. This keeps the Studio module entirely off the GPU, so it never competes with the interactive tier.
- **Video overviews:** cut (per §3.1). If a visual artifact is wanted, generate a static slide deck (already in FR3's Reports/Data-Tables scope) and pair it with the Kokoro audio track rather than attempting narrated video generation.

### 3.3 Proxmox layout

Because the M40 can only be passed through to one VM, the architecture is one GPU-owning inference service plus several lightweight CPU-only clients, all on the shared 192GB pool:

- **Inference VM** (what you already have: Ubuntu + llama.cpp + llama-swap, M40 passed through) — exposes an OpenAI-compatible endpoint on the internal network. Allocate generously (64–128GB) since this is the only VM that will ever need to hold a large CPU-offloaded MoE model's weights; it can run far smaller day-to-day.
- **Model gateway** — LiteLLM, pointed at the inference VM's endpoint plus any cloud keys you choose to keep as fallback (C1). Trivial footprint (<1GB).
- **Retrieval** — SearxNG + Perplexica/Vane (FR1/FR4) and a vector DB (Qdrant) for FR2. A few GB combined.
- **UI** — Open WebUI, pointed at the LiteLLM gateway rather than directly at llama-swap, so every client (including future ones) goes through the same OEM-agnostic layer. 2–4GB.
- **Orchestration** — LangGraph/CrewAI process for FR5/FR6, also calling the gateway rather than the inference VM directly. 2–4GB.
- **Studio module** — Kokoro TTS + whatever generates the slide/report formats for FR3, CPU-only. 2–4GB.
- **Memory/connector services** — a small Postgres instance for FR7's typed memory store, plus MCP servers for FR9. A few GB total.

Non-inference services sum to roughly 20–35GB even generously provisioned, leaving well over 150GB of headroom under the inference VM's allocation — more than enough even for an occasional 235B-class Q4 batch job (~130–140GB of weights), where CPU compute, not RAM capacity, is the actual bottleneck (§3.2).

One tuning point worth doing once, not optional-nice-to-have: the E5-2680 pair is a dual-socket NUMA system, and the M40 is physically wired to one socket's PCIe root complex. Pin the inference VM's vCPUs and memory to that same NUMA node in Proxmox — cross-socket (QPI/UPI) access on every PCIe transfer and every CPU-offloaded MoE layer otherwise pays a latency tax this hardware can't afford to give away for free.

### 3.4 The honest ceiling, and the one upgrade that actually lifts it

This machine is a genuinely capable **single-household** deployment target for everything in Part 2 except FR3's video-overview piece and FR12 (neither of which hardware fixes). It is not, and shouldn't be scoped as, a multi-user or low-latency-at-scale system — that's a different machine, not a configuration change to this one.

If you ever want to lift the two load-bearing constraints (no vGPU/MIG partitioning, no tensor cores / vLLM compatibility), the fix is a GPU swap, not a settings change — and it's worth being precise about what actually clears vLLM's compute-capability floor: a Pascal-class card like the P40 (24GB, compute capability 6.1) is a common, cheap R720-compatible upgrade path, but **6.1 is still below vLLM's 7.0 floor** ([vLLM issue #1284](https://github.com/vllm-project/vllm/issues/1284)) — it would improve FP16 throughput over the M40 but wouldn't change the vLLM or MIG story at all. Reaching Volta-or-newer (Turing/Ampere, e.g. a used RTX 3090/A4000-class card) is what actually unlocks vLLM, tensor cores, and — on the right SKU — vGPU-style partitioning. Separately, note that AVX2 is not purchasable as a part swap on this chassis: the R720's socket/chipset ceiling is Xeon E5-2600 v2, and Haswell's AVX2 only arrived with v3 — closing that gap means a newer chassis (R730-class or later), not new CPUs in the current box. Worth knowing before planning around "just add a faster CPU."

## Part 4 — Updating the homelab build for this architecture

This picks up directly from the GPU-passthrough session that built `llm01` (Ubuntu 24.04, driver 580-series, CUDA 12.9, llama.cpp built for `CMAKE_CUDA_ARCHITECTURES=52`, llama-swap on :8080, `qwen3-8b` confirmed working). Nothing about that base layer is wrong — §3.0–3.1 above confirm it's the only correct engine for this card. What's missing is the rest of §3.3's stack. **`llm01` stays the single GPU-owning VM; everything new is GPU-free and talks to it only through a gateway, never directly.**

### 4.1 Expand `llm01` for the three-tier model plan (§3.2)

Shut the VM down first (`sudo poweroff`), then in Proxmox:

- **Hardware → Memory → Edit:** raise to `98304` MiB (96GB). This covers the heavy-batch tier's CPU-resident expert weights (§3.2) while leaving ~90GB+ of the host's 192GB for everything in §4.2. Ballooning stays off, same reasoning as the original build.
- **Hardware → Disk → resize** (or add a second disk) to at least 500GB if your storage pool has room — three model tiers plus OS pushes well past the original 300GB once the heavy-batch model is in play. Check free space first: `pvesm status` on the Proxmox host.

Boot, then on the VM:
```bash
sudo growpart /dev/sda 3        # adjust device/partition number to match your layout
sudo pvresize /dev/sda3
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
df -h /
```

**Rebuild llama.cpp** to make sure the binary has `--n-cpu-moe` (added after a lot of installs predating it):
```bash
cd /opt/llama.cpp && git pull
cmake --build build -j 8
./build/bin/llama-server --help | grep -i n-cpu-moe   # confirm it's present
```

**Pull the three model tiers** into `/srv/models`:
```bash
cd /srv/models
# Interactive tier — ~30B total / ~3B active MoE, full GPU residency
wget -c "https://huggingface.co/unsloth/Qwen3-30B-A3B-Instruct-2507-GGUF/resolve/main/Qwen3-30B-A3B-Instruct-2507-Q4_K_M.gguf"
# Fast tier — you already have this from the original build (qwen3-8b); no change needed
# Heavy-batch tier — check unsloth/Qwen3-235B-A22B-GGUF (or bartowski's equivalent) on HF for the
# current best quant file and exact size before pulling; a Q4-class quant of this model is ~130GB,
# so confirm it actually fits your resized disk before starting the download.
```

**Replace `/opt/llama-swap/config.yaml`** with the three-tier version:
```yaml
healthCheckTimeout: 180
models:
  "interactive":
    cmd: >
      /opt/llama.cpp/build/bin/llama-server --port ${PORT}
      -m /srv/models/Qwen3-30B-A3B-Instruct-2507-Q4_K_M.gguf
      -ngl 99 -c 16384 -fa on
      --cache-type-k q8_0 --cache-type-v q8_0 --parallel 1
    ttl: 600
  "fast":
    cmd: >
      /opt/llama.cpp/build/bin/llama-server --port ${PORT}
      -m /srv/models/Qwen3-8B-Q4_K_M.gguf
      -ngl 99 -c 16384 -fa on --parallel 1
    ttl: 600
  "heavy-batch":
    cmd: >
      /opt/llama.cpp/build/bin/llama-server --port ${PORT}
      -m /srv/models/<chosen-235b-quant>.gguf
      -ngl 99 --n-cpu-moe 48 -c 8192 -fa on --parallel 1
    ttl: 1200
```
`--n-cpu-moe` takes a layer count, not a boolean (§3.2) — start at a high number (e.g. `48`) so the model loads without OOM, check `nvidia-smi` for VRAM headroom, then lower it step by step to push more experts back onto the GPU until VRAM is nearly full. Expect this tier to be noticeably slower than the aliteq/Medium reference numbers cited in §3.2, for the reasons given there (no AVX2, DDR3). `sudo systemctl restart llama-swap`, then confirm all three respond:
```bash
for m in interactive fast heavy-batch; do
  curl -s http://localhost:8080/v1/chat/completions -H "Content-Type: application/json" \
    -d "{\"model\":\"$m\",\"messages\":[{\"role\":\"user\",\"content\":\"hi\"}]}" | head -c 200; echo
done
```
Expect the first `heavy-batch` call to take minutes to load — that's disk read of a 130GB+ file, not a hang.

### 4.2 New Proxmox LXC containers for the rest of §3.3's stack

These are CPU-only and don't need PCI passthrough, so **LXC, not another VM** — lighter weight, faster to snapshot individually, and Proxmox already runs them. Enable Docker inside unprivileged LXCs once per container (Datacenter → container → Options → Features → tick **nesting** and **keyctl**), since every service below ships as an official Docker image and hand-building each from source (the reason `llm01` was built natively) doesn't apply here — none of them need a custom CUDA build.

| Container | Purpose | Cores | RAM | Disk |
|---|---|---|---|---|
| `lxc-gateway` | LiteLLM (C1's model-abstraction layer) | 1 | 2GB | 8GB |
| `lxc-ui` | Open WebUI | 2 | 4GB | 20GB |
| `lxc-retrieval` | SearxNG + Perplexica/Vane (FR1/FR4) | 2 | 4GB | 20GB |
| `lxc-vectordb` | Qdrant (FR2's RAG store) | 2 | 8GB | 50GB+ (scales with corpus) |
| `lxc-studio` | Kokoro-FastAPI (FR3 audio overviews) | 2 | 4GB | 10GB |
| `lxc-orchestration` | custom LangGraph/CrewAI service (FR5/FR6) | 2 | 4GB | 20GB |
| `lxc-memory` | Postgres (FR7) + MCP servers (FR9) | 1 | 4GB | 30GB |

Total: ~12 cores (oversubscribed against the host's physical cores is fine — these are bursty, not compute-bound), ~30GB RAM, ~160GB disk. Comfortably inside the ~90GB RAM headroom left after `llm01`'s 96GB allocation.

Create each with `pct create` (Debian 12 template is the lightest fit) or the Proxmox GUI, then inside each: `apt install -y docker.io docker-compose-plugin`.

**`lxc-gateway`** — `docker-compose.yaml`:
```yaml
services:
  litellm:
    image: ghcr.io/berriai/litellm:main-latest
    ports: ["4000:4000"]
    volumes: ["./litellm_config.yaml:/app/config.yaml"]
    command: ["--config", "/app/config.yaml"]
```
`litellm_config.yaml` registers `llm01` as a backend and gives OEM-agnostic aliases every other service will call by name instead of a model-specific identifier:
```yaml
model_list:
  - model_name: chat-default
    litellm_params: {model: openai/interactive, api_base: "http://<llm01-ip>:8080/v1", api_key: "none"}
  - model_name: chat-fast
    litellm_params: {model: openai/fast, api_base: "http://<llm01-ip>:8080/v1", api_key: "none"}
  - model_name: chat-batch
    litellm_params: {model: openai/heavy-batch, api_base: "http://<llm01-ip>:8080/v1", api_key: "none"}
  # Optional cloud fallback for anything the local tiers can't handle (C1):
  # - model_name: chat-frontier
  #   litellm_params: {model: anthropic/claude-sonnet-5, api_key: os.environ/ANTHROPIC_API_KEY}
```

**`lxc-ui`** — Open WebUI, pointed at the gateway, **not** at `llm01` directly:
```yaml
services:
  open-webui:
    image: ghcr.io/open-webui/open-webui:main
    ports: ["3000:8080"]
    environment:
      - OPENAI_API_BASE_URL=http://<lxc-gateway-ip>:4000/v1
      - OPENAI_API_KEY=none
    volumes: ["open-webui-data:/app/backend/data"]
volumes: {open-webui-data: {}}
```

**`lxc-retrieval`** — Perplexica (the project has been transitioning to the name "Vane"; the repo and compose file below are current as of this research) on its own SearxNG instance:
```bash
git clone https://github.com/ItzCrazyKns/Perplexica
cd Perplexica
# edit config.toml: point its chat-model entry at http://<lxc-gateway-ip>:4000/v1, model "chat-fast"
docker compose up -d
```
([Perplexica/Vane docker-compose.yaml](https://github.com/ItzCrazyKns/Perplexica/blob/master/docker-compose.yaml))

**`lxc-vectordb`**:
```yaml
services:
  qdrant:
    image: qdrant/qdrant
    ports: ["6333:6333"]
    volumes: ["qdrant-data:/qdrant/storage"]
volumes: {qdrant-data: {}}
```
Point Open WebUI's RAG settings and the orchestration service's retrieval calls at `http://<lxc-vectordb-ip>:6333`.

**`lxc-studio`** — Kokoro-FastAPI, the maintained Dockerized OpenAI-compatible wrapper around Kokoro-82M (§3.2):
```yaml
services:
  kokoro:
    image: ghcr.io/remsky/kokoro-fastapi-cpu:latest
    ports: ["8880:8880"]
```
([remsky/Kokoro-FastAPI](https://github.com/remsky/Kokoro-FastAPI)) Script a two-host "audio overview" as alternating calls to this endpoint with two different `voice` values, concatenated.

**`lxc-orchestration`** — this one's bespoke application code (the LangGraph/CrewAI graph implementing FR5/FR6/FR8), not a drop-in image; no off-the-shelf container exists because it's your product logic. Build it as a Python service calling `http://<lxc-gateway-ip>:4000/v1` for every generation step, `http://<lxc-vectordb-ip>:6333` for retrieval, and the MCP servers in `lxc-memory` for tools.

**`lxc-memory`**: standard `postgres:16` image for FR7's typed memory store, plus whichever MCP servers FR9 needs running as sidecar processes in the same container or split into their own if one turns out to be resource-heavy.

### 4.3 Network and firewall updates

The original build's `ufw allow from <subnet>/24 to any port 8080` already covers the new containers if they're on the same subnet as the VM (`192.168.100.0/24` per your network notes) — nothing to change there. Tighten it if the containers end up on a separate VLAN: replace the `/24` with the specific container subnet or individual IPs. Add equivalent LAN-only `ufw` rules on each new container for its own port (4000, 3000, 6333, 8880) — none of these need external exposure; only `lxc-ui`'s Open WebUI is a candidate for the reverse-proxy-plus-TLS treatment from the original guide's §11 if you want access from outside your LAN.

### 4.4 Build order

1. Expand and rebuild `llm01` (§4.1); confirm all three model tiers respond before touching anything else.
2. Create the LXCs (§4.2), enable nesting/keyctl, install Docker in each.
3. Deploy `lxc-gateway` first and test it directly (`curl http://<lxc-gateway-ip>:4000/v1/chat/completions ...`) before anything else depends on it.
4. Deploy `lxc-ui`, point it at the gateway, confirm chat works end-to-end.
5. Deploy `lxc-vectordb`, then `lxc-retrieval` (needs the gateway for its answering model).
6. Deploy `lxc-studio` (no dependencies on the others).
7. Deploy `lxc-memory`, then `lxc-orchestration` last, since it's the one component that calls everything else.
